## [0.5.0-preview.6] - 2026-09-21

Two tracks. [#650](https://github.com/dignite-projects/vault-extract/issues/650) tidies the multi-stage event contract: `FieldsExtractedEto` is retired and `OCRCompletedEto` becomes `DocumentTextExtractedEto`, both **breaking for an EventBus subscriber** — the migration for each is in its entry below. [#651](https://github.com/dignite-projects/vault-extract/issues/651) makes duplicate detection configurable per document type (layer-wide or per uploader) and repairs the duplicate-review defects [#635](https://github.com/dignite-projects/vault-extract/issues/635) left behind.

One deployment step: [#651](https://github.com/dignite-projects/vault-extract/issues/651) ships an EF migration, `V651_AddDocumentTypeDuplicateScope` (a NOT NULL `int` column defaulting to `0`, which is the pre-#651 behaviour, so no existing type or document changes meaning on upgrade).

### Removed

- **BREAKING — `FieldsExtractedEto` (wire `VaultExtract.Document.FieldsExtracted`) is retired** ([#650](https://github.com/dignite-projects/vault-extract/issues/650)). Migration: subscribe to `DocumentReadyEto`, which now also re-fires when an operator edits fields on an already-Ready document. Note the replacement is narrower: `FieldsExtractedEto` fired on every extraction — including the no-definitions clear path and for documents held in review (suspected duplicate, oversized body) — whereas `DocumentReadyEto` fires only for a Ready, non-container document. A consumer that mirrored field state for *every* document has no event-driven equivalent and must pull.
- **The localization key `Document:ReviewReason:NoViewableDuplicateCandidates` is removed** ([#651](https://github.com/dignite-projects/vault-extract/issues/651)). It said one thing — "no matching document you can view" — for two situations the operator has to act on differently, which is the defect §7 exists to fix. Two keys replace it in all four resource files: `Document:ReviewReason:HiddenDuplicateCandidates` (takes the hidden count as `{0}`: matches exist outside your visibility, an administrator must resolve this) and `Document:ReviewReason:NoRemainingDuplicateCandidates` (nothing matches any more, you may confirm it is not a duplicate). A deployment that overrode the old key in its own resource must move the override to whichever of the two it meant.

### Changed

- **BREAKING — `OCRCompletedEto` renamed `DocumentTextExtractedEto`; wire `VaultExtract.Document.OCRCompleted` → `VaultExtract.Document.TextExtracted`; `UsedOcr` / `FigureOcrCount` removed** ([#650](https://github.com/dignite-projects/vault-extract/issues/650)). Migration: rename the subscription. The two removed fields have no replacement on any egress surface — they were never persisted and had no known consumer.
- **`FieldExtractionService` constructor** — the `IDistributedEventBus` and `IClock` parameters are removed; the service no longer publishes anything ([#650](https://github.com/dignite-projects/vault-extract/issues/650)). BREAKING for a subclass only: drop those two arguments from the `base(...)` call.
- **The duplicate-candidate query takes the detection scope as its own parameter** ([#651](https://github.com/dignite-projects/vault-extract/issues/651)). `IDocumentRepository.FindDuplicateCandidatesAsync` gains `DuplicateDetectionScope detectionScope` and `Guid? subjectCreatorId` **before** the existing `DocumentAccessScope readScope`, which keeps its #635 meaning unchanged. The two are orthogonal and are applied in that order: detection scope answers "what counts as a duplicate", read scope answers "whose names may I show you" — the panel would otherwise list candidates under `Uploader` that never triggered the flag. BREAKING for a downstream that calls or overrides the method. `DocumentAppService.BuildDuplicateCandidatesAsync` returns `(List<DuplicateCandidateDto> Visible, int Hidden)` instead of a bare list, for the same issue's §7 below.
- **Constructors gained the new collaborators** ([#651](https://github.com/dignite-projects/vault-extract/issues/651)): `FieldExtractionService` and `DocumentAppService` take a `DuplicateDetectionEvaluator`, `DocumentTypeAppService` takes a `DocumentTypeUpdater` and a `DuplicateScopeVerdictCalculator`, and `DocumentTypePackAppService` takes a `DocumentTypeUpdater`. BREAKING for a subclass only: add the arguments to the `base(...)` call.

- **BREAKING — `DocumentType.Update` takes a required `duplicateScope`** ([#651](https://github.com/dignite-projects/vault-extract/issues/651)), restoring its original all-required shape. A default there would not merely pick a value for a new row — it **overwrites a persisted one**, so a save path whose author never noticed the parameter resets every `Uploader` type back to `Layer` and silently changes what counts as a duplicate across that type's whole corpus. The pack import did exactly that until it was caught. Migration: pass the type's current (or intended) scope explicitly. The **constructor keeps all its defaults**, with `duplicateScope` defaulting to `Layer`, and is not a break: it picks a value for a row that does not exist yet, where `Layer` is the documented product default — and requiring it would have forced `description` / `confidenceThreshold` / `priority` to lose their defaults too (an optional parameter may not precede a required one), breaking every consumer that constructs a type by its four identifying values over something unrelated. `DocumentType.SetDuplicateScope` is removed: the scope now moves only through a path that compares before and after.

- **A changed fingerprint now withdraws `DuplicateAllowed`, on every write path** ([#651](https://github.com/dignite-projects/vault-extract/issues/651)). `Document.SetFieldFingerprint` returns `bool` (whether the value changed) and clears the operator's "not a duplicate" override whenever it did — an ordinal comparison of the normalized value, so `null` → `null` and equal → equal are no-ops. **This is a behaviour change beyond the manual-correction fix:** a *re-extraction* that lands on a different key now re-raises the duplicate flag on a document an operator had cleared, where before the override suppressed it forever. Re-extraction onto the same key still leaves the override standing, which is what #411 meant by "the decision survives re-extraction". The two paths that write `null` — extraction's no-definitions branch and #528's duplicate-basis cleanup — withdraw it too: a verdict about a key the type no longer has applies to nothing. The rule lives on the aggregate rather than at the four call sites, so a fifth one gets it for free. BREAKING for a downstream only in that the method's return type changed; callers ignoring it are source-compatible.

### Added

- **`DocumentReadyEto` re-announce from `UpdateExtractedFieldsAsync`** ([#650](https://github.com/dignite-projects/vault-extract/issues/650)): an operator editing fields on an already-Ready document now re-publishes the event, so downstream consumers know to pull the updated fields.
- **The egress event contract page** `docs/en/egress/integration-events.md` ([#650](https://github.com/dignite-projects/vault-extract/issues/650)).
- **Duplicate detection can be scoped per uploader** ([#651](https://github.com/dignite-projects/vault-extract/issues/651)). `DocumentType` gains `DuplicateScope`, a `DuplicateDetectionScope` of `Layer` (0) or `Uploader` (1), carried on `CreateDocumentTypeDto` / `UpdateDocumentTypeDto` / `DocumentTypeDto` / `DocumentTypePackDto` (exported and imported, so a pack round-trips it). Until now detection was layer-wide with no way to say otherwise: in a tenant where several departments each keep their own copy of the same vendor invoice, the second upload was blocked at review every time. Under `Uploader` a fingerprint collides only with another document sharing the subject's `Document.CreatorId` — the same anchor [#635](https://github.com/dignite-projects/vault-extract/issues/635)'s ownership arm uses, which derived sub-documents already inherit. **The enum's integer values are a frozen persisted + serialized contract.** Scoping by cabinet, department or anything else would be a third member, never a second axis.

  > **A null `CreatorId` matches only another null `CreatorId`** — equality on the anchor like any other value, with no fallback to layer-wide, which would apply the stricter rule to exactly the rows nobody asked to be stricter about. Note who those rows are: not only historical data, but **every machine-identity upload**, since `CreatorId` comes from `CurrentUser.Id` and a `client_credentials` caller has none. Under `Uploader`, all machine-ingested documents of a type therefore form one bucket. Intended, not a defect.

  > **Deployment:** one EF migration, `V651_AddDocumentTypeDuplicateScope`, adds a NOT NULL `int` column with default `0` to `VaultDocumentTypes`. `Layer = 0` is the pre-#651 behaviour, so **no existing type changes meaning and no existing document changes state on upgrade.**

- **Changing a type's duplicate scope reconciles the existing flags** ([#651](https://github.com/dignite-projects/vault-extract/issues/651)). `DuplicateSuspected` is a persisted bit, not a computed view, so a switch leaves a stale half in **both** directions: narrowing (`Layer` → `Uploader`) leaves flagged documents parked under a rule the admin just retracted — an uploader cannot resolve one, because the panel now returns nothing for it and `DocumentAccessRule.Review` has no owner arm — and widening (`Uploader` → `Layer`) leaves unflagged documents that now collide with another uploader's copy. `DuplicateScopeReconciliationJob` (`VaultExtract.DuplicateScopeReconciliation`) is enqueued automatically on save, only when the value actually moved, and re-evaluates the type in keyset batches: per batch a narrow projection, then a collision aggregate restricted to that page's fingerprints, and a row load **only** for the documents whose verdict changes — so each batch is O(batch size) and a run is linear in the type's size, rather than one whole-type aggregate per batch. It is flag-only — no LLM call, no field value touched, no event published — which is what separates it from [#289](https://github.com/dignite-projects/vault-extract/issues/289) bulk reprocessing and puts it in the [#528](https://github.com/dignite-projects/vault-extract/issues/528) family instead. Recycle-bin documents are reconciled too (restoring one must not resurrect a retracted verdict); `DuplicateAllowed` documents are skipped entirely, and nothing here ever calls `Document.AllowDuplicate`. The job reads the type's setting at execution time, so two switches in quick succession converge on the later one.

  > **A switch in either direction can pull an already-Ready document back into review**, and its `DocumentReadyEto` has already been consumed downstream. There is no "un-Ready" event; this is existing semantics — re-extracting a Ready document does the same, and at-least-once consumers already tolerate it — but it is a real consequence, so the admin is shown it **before** saving: `IDocumentTypeAppService.GetDuplicateScopePreviewAsync` (`GET /api/vault-extract/document-types/{id}/duplicate-scope-preview?duplicateScope=…`, gated by `DocumentTypes.Update`) returns `willFlagCount` and `willClearCount` — how many **live** documents of the type would have the blocking duplicate reason set and cleared. Those are the real diff, produced by the same component the job then applies, run over every page under the prospective scope and counted instead of written; they are not a direction heuristic, because **both directions re-evaluate every fingerprinted document** and so both can flag as well as clear. (A narrowing switch flagging is not a corner case: the stored bit is a snapshot taken at each document's own extraction, so the *first* upload of a key sits unflagged — its twin did not exist yet — while the twin carries the flag, and re-evaluation gives the first one the verdict it would have today.) The preview reads only, but it does page the whole type while the admin waits.

- **A blocked uploader is told why their duplicate panel is empty** ([#651](https://github.com/dignite-projects/vault-extract/issues/651) §7, repairing a defect [#635](https://github.com/dignite-projects/vault-extract/issues/635) left on `main`). For an uploader who reaches documents only through the ownership arm, the pipeline detected layer-wide and set the blocking reason, the detail panel re-ran the query under their Read scope and returned nothing, and `Review`'s `OwnerArm: Never` meant they could not clear it either — a blocking reason with an empty explanation and no action. The `DuplicateSuspected` review-reason detail now also carries `hiddenDuplicateCandidateCount`, so the client can distinguish "nothing collides any more" (allow it) from "candidates exist, outside your visibility" (an administrator must resolve it). Computed only on the flagged branch, and only for a caller whose read scope is narrowed at all; both counts share the `MaxDuplicateCandidates` cap, so it is a floor rather than an exact total. No new endpoint.

### Fixed

- **A manual field correction now recomputes the duplicate fingerprint** ([#651](https://github.com/dignite-projects/vault-extract/issues/651) §6, a pre-existing [#411](https://github.com/dignite-projects/vault-extract/issues/411) defect independent of the scope setting). Across the whole repository the fingerprint was computed in exactly one place, the field-extraction write phase, so `DocumentAppService.UpdateExtractedFieldsAsync` left a corrected document hashed under the **wrong** value forever: the LLM reads invoice number `1284` where the document says `1234`, the operator fixes it, and the genuine re-upload carrying `1234` never collides with it. The edit now recomputes the fingerprint from the corrected values and, **only if it changed**, revokes any `DuplicateAllowed` override — the operator's "not a duplicate" verdict was about the old key values — and re-runs detection. An edit that touches no unique-key field does none of this. The decision itself moved into one `DuplicateDetectionEvaluator` shared by extraction, manual correction and reconciliation, so the three entry points cannot drift the way the pipeline and the panel did.

## [0.5.0-preview.5] - 2026-09-20

Rebuilds the document permission core on ABP's resource-based authorization ([#629](https://github.com/dignite-projects/vault-extract/issues/629) → [#632](https://github.com/dignite-projects/vault-extract/issues/632) → [#635](https://github.com/dignite-projects/vault-extract/issues/635) → [#636](https://github.com/dignite-projects/vault-extract/issues/636) → [#645](https://github.com/dignite-projects/vault-extract/issues/645) → [#648](https://github.com/dignite-projects/vault-extract/issues/648)). One rule now governs every documents-domain operation, and the operator UI follows the same pattern: **entry (`VaultExtract.Documents`) AND either the module-wide permission for that operation, the matching grant on the document's own type, or having uploaded it.**

Four contract breaks come with it — entry is required everywhere, `VaultExtract.Documents` stops meaning "read every document" (the new `Documents.ReadAll` does), `Documents.Restore` is removed in favour of `Documents.Delete`, and `VaultExtractPermissions.DocumentTypes.Resources` moves to `VaultExtractResourcePermissions`. Each BREAKING entry below carries its migration note, and two changes need a deployment step: the sub-document owner backfill under #635 and the duplicate Host-layer roles left behind by the seed defect in [#640](https://github.com/dignite-projects/vault-extract/issues/640).

### Added

- **Per-document-type Read / Edit / Delete grants** ([#632](https://github.com/dignite-projects/vault-extract/issues/632), completing the topic opened by [#629](https://github.com/dignite-projects/vault-extract/issues/629)). Three resource permissions join `…DocumentType.Upload` on the `DocumentType` resource — `…DocumentType.Read`, `…DocumentType.Edit`, `…DocumentType.Delete` — all managed by the existing `VaultExtract.DocumentTypes.ManagePermissions`, so ABP's dialog simply renders four checkboxes. One rule governs all of them: **an operation on a document is authorized by `VaultExtract.Documents` (entry) AND either the module-wide permission for that operation OR the matching grant on the document's current type.** Entry gates both halves of the OR — a caller who may not open the documents area may not mutate documents in it either, which matters because handing out a per-type grant is gated by `DocumentTypes.ManagePermissions` alone, a permission unrelated to `Documents.*`. Restore joins the table without a fifth name: `RestoreAsync` is admitted by the `Delete` grant on the document's type — whoever may delete may undo ([#645](https://github.com/dignite-projects/vault-extract/issues/645) then did the same at the role level, merging `Documents.Restore` into `Documents.Delete`; see its entry below). Reaching the recycle bin requires entry alone, and its rows are the caller's readable soft-deleted documents, own included ([#635](https://github.com/dignite-projects/vault-extract/issues/635) — #632 had admitted by the Restore arm across the layer, `Documents.Restore` or a `Delete` grant on at least one type, while narrowing the rows by the read arm, so a `Delete`-grant-only caller was let into a bin the UI then reported as empty). `PermanentDeleteAsync` remains module-wide only. It is implemented once, in an application-layer `DocumentAccessChecker` that every enforcement point calls (`UploadAsync`'s inline OR from #629 moved onto it), because ABP's `ResourcePermissionChecker` has no module-wide fallback of its own. Reads are additionally narrowed at the query — the operator list, the data download, the MCP `search_documents` tool and the review-queue count all pass through the one shared `DocumentQueries.ApplyMetadataFilter` chain, so a page's total count is narrowed by the same predicate as its rows. The MCP read paths (`get_document` and the `vault-extract://documents/{id}` resources) fold the new authorization refusal into the "Document not found" answer they already give for a nonexistent or cross-tenant id, so a document outside the caller's read scope cannot be told apart from one that does not exist. `DocumentTypeDto.resourcePermissions` now carries all four keys. (#632 also gave `IDocumentTypeAppService.GetVisibleAsync` an optional `includeResourcePermissions` flag for the MCP paths; [#636](https://github.com/dignite-projects/vault-extract/issues/636) removed it again before release in favour of `GetVisibleSummariesAsync` — see its entry below.) Grants still live in `AbpResourcePermissionGrants`, which has existed since the `Initial` migration — **no schema change and no EF migration is required**. See [the configuration page](docs/en/configuration/document-type-permissions.md).

  > **Untyped documents belong to no type**, so no per-type grant can ever cover one. Under #632 that meant only a `Documents.ReadAll` holder reached them; [#635](https://github.com/dignite-projects/vault-extract/issues/635) adds the second arm that can — **the uploader** — which is what finally makes a failed classification reachable by the person who can fix it. Sub-documents carry their own type and are covered by it.

  > **The four resource-permission strings are frozen contracts from the first grant row onwards**, the same discipline the `Extract:*` error codes follow — they are persisted verbatim in the grant table.

  In the operator UI, the document list and the document detail page gate every per-document action by the same rule (delete, confirm, reclassify, re-recognize, re-extract, field and Markdown editing, reject, allow duplicate, resolve warnings) — [#635](https://github.com/dignite-projects/vault-extract/issues/635) moved that judgment onto the server and the client now binds to the `rights` object on the row, see below. The Confirm / Reclassify type pickers list only the types the caller may assign, bulk-delete selection drops rows the caller may not delete, the **Needs review** toggle and quick link follow an Edit grant on any visible type, and the overview's statistics card renders only for a `Documents.ReadAll` holder — without it the request behind it is never made. Routes are unchanged; `Documents` still gates entry.

- **Per-document-type upload permissions** ([#629](https://github.com/dignite-projects/vault-extract/issues/629)), built on ABP's resource-based authorization rather than a hand-written grant table. Two names are introduced: the standard permission `VaultExtract.DocumentTypes.ManagePermissions`, which gates who may hand out access, and the resource permission `Dignite.Vault.Extract.Documents.DocumentTypes.DocumentType.Upload`, granted per document type to a user or a role. A caller's type scope for upload is "every type of the layer if they hold `Documents.Upload`, otherwise the types they hold the `Upload` grant on", and the grant is enough on its own ([#645](https://github.com/dignite-projects/vault-extract/issues/645) — #629 first gave the all-types half to `Documents.ConfirmClassification` and still required `Documents.Upload` beside the grant; see the upload entry under *Changed*). Grants live in `AbpResourcePermissionGrants`, which has existed since the `Initial` migration — **no schema change and no EF migration is required**. `DocumentTypeDto` gains a `resourcePermissions` dictionary reporting the caller's own grants on `GetVisibleAsync`, and `IDocumentTypeAppService.GetVisibleAsync` additionally admits `Documents.Upload` holders so an upload-only caller can see the list to pick from. Managing the grants goes through ABP's own resource-permission endpoints and dialog; nothing is added to `IDocumentTypeAppService`. See [the configuration page](docs/en/configuration/document-type-permissions.md). The document types list gained a **Permissions** row action (gated by `ManagePermissions`) that opens ABP's resource-permission dialog for the row's type, and the upload picker lists every type plus the untyped "Let AI classify" option for a `Documents.Upload` holder, and otherwise only the types the caller holds an `Upload` grant on, from which it requires a selection ([#645](https://github.com/dignite-projects/vault-extract/issues/645); #629 first keyed this on `ConfirmClassification` and showed an empty state to an uploader granted no type, which the overview now answers with its read-only card).

  > **Both new strings are frozen contracts from the first grant row onwards**, the same discipline the `Extract:*` error codes follow — they are persisted verbatim in the grant table. The resource name must in particular stay equal to `typeof(DocumentType).FullName`, which a unit test asserts.

### Changed

- **Whoever uploaded a document may now read, edit and delete it** ([#635](https://github.com/dignite-projects/vault-extract/issues/635)). The document permission core is rebuilt around one rule, stated once: **entry (`VaultExtract.Documents`) AND ( the module-wide permission for the operation OR the caller owns the document, where the rule allows it OR the matching per-type grant on the document's current type )**. The per-type `Read` / `Edit` / `Delete` grants keep their names and their rows and come to mean "over **other people's** documents of this type"; their display names say so. Two day-one failures fall out of the new arm: a principal holding entry plus an `Upload` grant — the exact shape [#629](https://github.com/dignite-projects/vault-extract/issues/629) exists to express — could upload a document and then never see it again, and a document whose classification **failed** was invisible to every caller without a module-wide permission, so the documents that most need a human were the ones their uploader could not reach. Ownership is `Document.CreatorId`, ABP's audit property: **no new permission, no new frozen string, no schema change and no EF migration**. Derived sub-documents inherit their origin's owner from now on, so the sub-documents of a bundle reach the person who uploaded the bundle. Machine identities (a client-credentials token has no `sub`) never match the ownership arm. `DocumentListItemDto` and `DocumentDto` gain a `rights` object (`canRead` / `canEdit` / `canReview` / `canDelete` / `canRestore` / `canRetry`) decided by the same checker the endpoints enforce with, so the client binds actions to the answer instead of re-deriving the rule from the caller's grants — which is what made a document on an archived type come back with every action missing, and what could not express ownership at all. **No `creatorId` is exposed.** The application-layer helper is renamed `DocumentTypeAccessChecker` → `DocumentAccessChecker` to match what it now judges, and `DocumentAccessRule` / `DocumentAccessSubject` / `DocumentAccessScope` / `DocumentAccessMemo` join it; `DocumentMetadataFilter.ReadableDocumentTypeIds` becomes `ReadScope`. A downstream referencing any of them sees a compile-time break and no runtime change. See [the configuration page](docs/en/configuration/document-type-permissions.md).

  > **Retroactive by design.** A principal holding entry + `Upload` that today sees nothing after uploading will, after this release, see, edit and soft-delete **everything it has ever uploaded**. Nothing is granted that was not implied by "this principal uploaded this document"; if that is not the intent for a given role, remove its entry permission — revoking its upload rights (`Documents.Upload`, or its `Upload` grants) stops further uploads but does not retract ownership of what it already uploaded (see *No lock after submission* below).

  > **Deployment — backfill the owner of sub-documents split out before this version.** Sub-documents split out of a container before this release were spawned by a background job with no principal and so have no owner: their uploader sees the container but none of its contents. Any deployment that split containers before upgrading needs this once — module consumers run it against their own host's database, since no EF migration ships for it. It is idempotent (a second run updates 0 rows), and it loops because provenance chains can be deeper than one level:
  >
  > ```sql
  > -- Table name assumes the default VaultExtractDbProperties.DbTablePrefix ("Vault").
  > DECLARE @rows INT = 1;
  > WHILE @rows > 0
  > BEGIN
  >     UPDATE child
  >        SET child.[CreatorId] = parent.[CreatorId]
  >       FROM [VaultDocuments] AS child
  >      INNER JOIN [VaultDocuments] AS parent ON parent.[Id] = child.[OriginDocumentId]
  >      WHERE child.[CreatorId] IS NULL AND parent.[CreatorId] IS NOT NULL;
  >     SET @rows = @@ROWCOUNT;
  > END
  > ```

  > **Review is deliberately not an owner's right.** `AllowDuplicateAsync`, `ResolveFieldValidationWarningsAsync` and `RejectReviewAsync` carry exactly the same two permission names as the edit family and differ **only** in that the ownership arm is shut: they clear a blocking review reason, and a suspected duplicate or a field-validation warning exists precisely so that someone other than the uploader checks the uploader's work.

  In the operator UI, the client-side copy of the rule table is **deleted**: every per-row action on the document list, the document detail page and the recycle bin binds to the `rights` object the server sent with that row, so what the UI offers and what the endpoint admits can no longer drift — a document on an archived type now shows exactly the actions the API admits, and an uploader sees their own upload's actions including on an untyped document. The detail page's Retry button follows `rights.canRetry` rather than only whether the run is retryable, its Change-cabinet button follows `rights.canEdit`, and Reject / Allow duplicate / Resolve warnings follow `rights.canReview` while Confirm classification and Complete fields stay on `rights.canEdit`. What the client still decides for itself is the two questions that are about *types* rather than documents — which types it may assign, and whether it may review anything at all — and those move onto a single root-provided **`DocumentTypesStore`**: one `GetVisibleAsync` call per session, shared by the list, the detail page, the overview and the upload card, with "still loading" and "the fetch failed" answered once instead of by four per-component flag pairs. The recycle bin no longer needs the type list at all and no longer fetches it; it always queries the server and has one empty state, so the `Document:RecycleBin:NoRestoreRights` message is removed from all four localization resources. The type-management page is the store's invalidation site: every successful create, update, archive, restore or pack import, and every close of the resource-permission dialog, reloads it; and a failed fetch heals on the next page arrival or explicit Refresh, which retry it only when it failed. The detail page's own fetch no longer lets a refusal through ABP's global error modal: when a poll or reload is refused because a re-recognition moved the document out of the caller's read scope, the page says the document is no longer visible to them and returns to the list, while every other error is reported exactly as before. On the detail page, a mutation whose redacted response says the caller can no longer read the document — a reclassification into a type they may declare but not read — is never rendered or re-fetched: the page shows that the action succeeded and returns to the list; a document held by a blocking review reason that the caller may neither edit nor review says it is waiting for a reviewer; and a suspected duplicate with no candidate the caller may see says there is no matching document they can view.

- **An uploader may not *modify* their own document while it is held for review** ([#635](https://github.com/dignite-projects/vault-extract/issues/635)). The ownership arm is three-valued, not a yes/no: an uploader may **always** read, delete and restore their own document, may **never** resolve its review, and may **not modify** it while it carries a blocking review reason other than `UnresolvedClassification` (`DuplicateSuspected`, `FieldExtractionIncomplete`, `FieldValidationWarning` — derived as "every blocking reason except classification", so one added later locks owners out by default). Closing only the three explicit review methods would not have held: the edit family clears the same bits as a side effect — an empty `UpdateExtractedFieldsAsync` body clears `FieldExtractionIncomplete` outright (#491's escape path) and releases the document to Ready, re-extraction replaces the whole validation-warning set and recomputes the duplicate fingerprint, and `ConfirmClassificationAsync` resets duplicate state even when reclassifying to the same type. A document blocked only on classification stays owner-editable, because confirming one's own upload is the intended act and the target type is judged by the `DeclareType` rule, which has no ownership arm at all. `rights.canEdit` / `rights.canRetry` come back false for a locked owner with no special case in the client.

- **The duplicate-candidate panel is narrowed by the caller's read scope, and an edit without read returns a redacted body** ([#635](https://github.com/dignite-projects/vault-extract/issues/635)). `IDocumentRepository.FindDuplicateCandidatesAsync` takes a `DocumentAccessScope`: the panel names other documents by title and file name, and a shared `(type, fingerprint)` is not a permission to see whoever else uploaded one. The field-extraction pipeline passes `Unrestricted` explicitly — it only counts, and a duplicate the uploader may not see is still a duplicate. Separately, every method of the edit and review families returns the document's DTO, so an `Edit`-grant holder with no `Read` grant used to receive the whole Markdown, title, field values and file origin as the response body of a cabinet reassignment; `MapToDtoAsync` now returns **only the id and the rights** when `canRead` is false. The write still happens; what comes back is not the read the caller was refused.

  > `CabinetAppService.DeleteAsync` gains an **entry** assertion: it clears `CabinetId` on every document of the cabinet, recycle-bin ones included. It is deliberately not a row on the rule table — unassigning on cabinet deletion is the cabinet's lifecycle, and narrowing the cascade by a read scope would leave the documents the caller cannot reach pointing at a row that no longer exists, which is the state [#530](https://github.com/dignite-projects/vault-extract/issues/530) removed.

- **No lock after submission** ([#635](https://github.com/dignite-projects/vault-extract/issues/635)). Revoking an upload right — `Documents.Upload`, or an `Upload` grant — does not retract ownership of what was already uploaded, and nothing short of removing the entry permission stops an uploader from editing or soft-deleting their own document — including one that has already fired `DocumentReadyEto`. Approval workflows belong to the downstream consumer, which already handles `DocumentDeletedEto`. Stated, not solved.

- **BREAKING — entry (`VaultExtract.Documents`) is now required by every documents-domain operation** ([#635](https://github.com/dignite-projects/vault-extract/issues/635)). `PermanentDeleteAsync`, `RetryPipelineAsync`, the four `DocumentReprocessingAppService` methods, `ExportAsync` and the untyped branch of `UploadAsync` used to declare their gate with an `[Authorize]` attribute (or, for the export, a class-level one plus a read scope that deliberately did not assert entry) and so asserted entry nowhere — `Documents.PermanentDelete` without `Documents` hard-deleted a document in an area the caller could not open. They are rows on the rule table now, and a principal holding one of those permissions **without** `VaultExtract.Documents` is refused where it was admitted before.

  > **Migration:** such a principal can only be produced by a programmatic `IPermissionManager` grant or a hand-edited store, so **no seeded role is affected**. ABP's permission dialog ticks the whole ancestor chain, not just the immediate parent (`findParentPermissions` walks `parentName` to the root and grants every name on the way), which matters because `Documents.Pipelines.Retry` and `Documents.Reprocessing.*` are **grandchildren** of `VaultExtract.Documents` — they hang off `Documents.Pipelines` and `Documents.Reprocessing`. Hand-made roles and OAuth clients holding `Documents.PermanentDelete`, `Documents.Pipelines.Retry`, `Documents.Reprocessing.*` or `Documents.Export` should still be checked once for the entry permission.

- **`RetryPipelineAsync` is reachable per-type and by owners** ([#635](https://github.com/dignite-projects/vault-extract/issues/635)), revisiting [#632](https://github.com/dignite-projects/vault-extract/issues/632)'s "module-wide only, by decision". Retry is a single-document operator action on the detail page — the same act as `RerecognizeAsync` beside it, which #632 already put on the `Edit` arm — and none of the reasons the remaining module-wide-only rows have (irreversible, admin-level bulk, whole-layer aggregate) applies to it. `Documents.Pipelines.Retry` keeps its meaning as the module-wide arm; an `Edit` grant on the document's type, or having uploaded it, now reaches it too. The detail page's retry button follows the row's `canRetry` instead of checking only whether the run is retryable.

- **`UpdateCabinetAsync` now requires `Edit`, not `Read`** ([#635](https://github.com/dignite-projects/vault-extract/issues/635)). It calls `SetCabinet` + `UpdateAsync`, so filing a document is a write however it is described; leaving it on the Read rule meant a `Read` grant was no longer read-only. Assigning to a cabinet still additionally requires `Cabinets.Default`. Two smaller shape changes ride along: the **recycle bin** is admitted by entry alone and its rows are the caller's readable soft-deleted documents (it used to admit by the Restore arm and narrow by the Read arm — two different questions — so a `Delete`-grant-only caller was let into a bin the UI then reported as empty while it was not), and **`ExportAsync`** no longer refuses a type the caller holds no `Read` grant on but narrows the rows in the file by the same Read scope the screen runs, because after ownership that refusal could no longer distinguish "you may see nothing of this type" from "you may see your own". An unknown type **code** still loud-fails.

- **`IDocumentTypeAppService.GetVisibleAsync` loses its `includeResourcePermissions` flag; the MCP paths move to a new `GetVisibleSummariesAsync`** ([#636](https://github.com/dignite-projects/vault-extract/issues/636)). The boolean let `false` skip ABP's `ResourcePermissionPopulator`, but it also leaked onto the REST contract as a `[FromQuery]` parameter whose empty-dictionary response meant "not asked", never documentable as "no grants" on a public surface. `GetVisibleAsync()` now regains its single meaning — always populated — and the three in-process MCP adapters (`DocumentTypeTools`, `DocumentTypeResources` ×2) call `GetVisibleSummariesAsync()` instead, which returns the new `DocumentTypeSummaryDto` (`id` / `typeCode` / `displayName` only, no `resourcePermissions` member at all, so the ambiguity cannot be expressed) and skips the populator structurally rather than by flag. Both AppService methods share the same visibility judgment through a `protected virtual GetVisibleEntitiesAsync`. `GetVisibleSummariesAsync` is not part of the REST contract — this repo has no conventional-controller auto-exposure for the Application(.Contracts) assembly, only the explicit `DocumentTypeController`, which implements it explicitly (off the controller's public action surface) purely to satisfy the C# interface. The Angular proxy is regenerated; `getVisible()` already called with no arguments everywhere in this codebase.

- **The MCP read paths (`get_document`, `vault-extract://documents/{id}`) no longer fold "no entry permission at all" into "Document not found"** ([#636](https://github.com/dignite-projects/vault-extract/issues/636)). `DocumentResources` and `DocumentTools` each carried an identical `catch (EntityNotFoundException or AbpAuthorizationException) → McpException("Document not found")`, which correctly folds "does not exist" and "outside your per-type Read scope" (#632) but incorrectly also swallowed a caller holding no `Documents.Default` at all — an entry-wide fact unrelated to any specific id, now undiagnosable as anything but a wrong id. The fold moves to a new `IDocumentAppService.FindForCallerAsync(Guid id)`, which still asserts entry and throws `AbpAuthorizationException` for it (propagated uncaught by both adapters, same as the existing `search_documents` tool's authorization failures), and returns `null` — not-found, cross-tenant, and out-of-read-scope alike — only once entry is confirmed. Both adapters shrink to `FindForCallerAsync(id) ?? throw new McpException(...)` with no `catch`. `GetAsync` (the REST use case) keeps its own throwing contract unchanged.

- **BREAKING — `VaultExtractPermissions.DocumentTypes.Resources` moves to its own holder, `VaultExtractResourcePermissions`** ([#636](https://github.com/dignite-projects/vault-extract/issues/636)). The per-document-type resource-permission family (a resource name plus the `Upload` / `Read` / `Edit` / `Delete` grants, #629/#632) only ever lived inside the class that models the standard permission tree because the names were related — it is never checked by name alone, never grantable from the ordinary permission grid, and its presence forced `VaultExtractPermissions.GetAll()` to filter it back out by string prefix for a reflection-based array with no production caller. Both are gone: the family moves verbatim to `Permissions.VaultExtractResourcePermissions`, and `GetAll()` is deleted along with `DocumentTypeResourcePermissions_Tests.GetAll_returns_standard_permissions_only`, the test that existed solely to guard it. **The four string values are unchanged to the character** — `VaultExtractResourcePermissions.Name` / `.Upload` / `.Read` / `.Edit` / `.Delete` are still the same persisted `AbpResourcePermissionGrants` contract; this is a compile-time rename of the C# holder, not a data migration.

  > **Migration:** any downstream code referencing `VaultExtractPermissions.DocumentTypes.Resources.*` sees a compile-time break and should switch to `VaultExtractResourcePermissions.*` — no runtime data is affected.

- **BREAKING — `VaultExtract.Documents` no longer means "read every document"; a new child `VaultExtract.Documents.ReadAll` does** ([#632](https://github.com/dignite-projects/vault-extract/issues/632)). `VaultExtract.Documents` keeps its place as the permission-group parent and the SPA route gate, and now means only "may enter the documents area and work inside the caller's own type scope". The split is what makes a per-type `Read` grant expressible at all: `VaultExtract.Documents` was the gate on every read endpoint and on every SPA documents route, so every principal that can open the documents area held it and therefore saw every document of the layer, and a per-type `Read` hung off it alone would never have narrowed anyone. (ABP's `PermissionDefinition.Parent` is enforced by the permission-management dialog, which checks the parent with the child; `PermissionChecker` never consults it, so a permission granted programmatically through `IPermissionManager` can exist without its parent. The split rests on the route guard and the read gates, not on the parent rule.) The overview statistics endpoint moves to `ReadAll` too: a whole-layer aggregate has no per-type meaning.

  > **Migration:** any role, user or MCP OAuth client that holds `VaultExtract.Documents` and is expected to keep seeing every document must be granted **`VaultExtract.Documents.ReadAll`**. Without it the document list, the data download and the MCP `search_documents` tool return only the types the principal holds a per-type `Read` grant on, plus — since [#635](https://github.com/dignite-projects/vault-extract/issues/635) — the documents the principal uploaded itself; for a principal with neither, nothing. The overview statistics card disappears. The seeded `DocumentManager` and `Viewer` roles gain `ReadAll` from `VaultExtractHostRoleDataSeedContributor`, applied idempotently on the next migration run, and `admin` receives it from the migrator's permission seed; **roles created by hand and MCP clients need the grant applied manually**, through the admin UI or `IPermissionManager`. No data is lost and nothing is deleted — visibility is restored the moment the grant is added.

- **Upload follows the pattern of every other document permission: `Documents.Upload` uploads into any type, the `Upload` grant into its one type on its own** ([#645](https://github.com/dignite-projects/vault-extract/issues/645), reshaping [#629](https://github.com/dignite-projects/vault-extract/issues/629)). `VaultExtract.Documents.Upload` means "upload into all document types", including an untyped upload that the classifier then assigns; the per-type `Upload` grant means "upload into this type" and no longer needs `Documents.Upload` beside it, so an ordinary uploader is configured as entry plus an `Upload` grant on each type they may upload into. `ConfirmClassification` leaves the upload path: a caller holding it without either upload right is refused every upload. An untyped upload still needs the role-level permission, for #629's reason — the classifier may land the document in any type, so a caller whose right is per type must name the type. `UploadAsync` now makes one judgment by the `Upload` rule (on the declared type, or on no type when untyped) after entry and the declared type's existence check, and before any business validation; the separate admission check and the declared-type check are gone. A reclassification's **target** type keeps its own rule, which now admits `ConfirmClassification` **or** `Documents.Upload` — someone who could have uploaded into any type may also move their document into any type — or the `Upload` grant on the target. `DocumentAccessRule`'s module-wide arm becomes a set (`ModuleWidePermissions`), of which that rule is the only one with two members.

  In the operator UI, the overview's upload card and the list's upload button appear for a caller holding `Documents.Upload` **or** an `Upload` grant on at least one visible type; both used to require `Documents.Upload` and so hid from exactly the ordinary uploader above. While the shared type store has not answered, a caller without `Documents.Upload` sees a neutral placeholder rather than either card; if the store fails, the upload card's "types could not be loaded" state and its retry; once it answers with no grant, the read-only card. The card offers the untyped option ("交由 AI 分类" / "Let AI classify") only with `Documents.Upload` and lists every type then, otherwise only the `Upload`-granted types. The confirm / reclassify pickers list every type for `ConfirmClassification` or `Documents.Upload`, otherwise only the `Upload`-granted types. `EXTRACT_PERMISSIONS.Documents.Restore` is removed from the Angular package.

  > **Not a breaking change against any released version.** In v0.3.x, v0.4.x and the v0.5.0 previews `Documents.Upload` alone admitted an untyped upload, and it does again. #629 had narrowed that on unreleased `main` — an untyped upload required `ConfirmClassification` — and that BREAKING entry is withdrawn: nothing released ever required it. Relative to the last release the change is additive: a `Documents.Upload` holder may also declare any type at upload (the declared type is [#623](https://github.com/dignite-projects/vault-extract/issues/623), itself unreleased), and an `Upload` grant is a complete uploader. The seeded `DocumentManager` role keeps `ConfirmClassification` — it is an operator role that edits and reviews — and only the seed's comment explaining why changed.

- **BREAKING — `VaultExtract.Documents.Restore` is removed; restoring is `Documents.Delete`** ([#645](https://github.com/dignite-projects/vault-extract/issues/645)). Whoever may delete may undo, now at the role level as well as the type level: the Restore rule is (`Documents.Delete`, the `Delete` grant, owner always) — the Delete rule's three values. The permission definition, the `VaultExtractPermissions.Documents.Restore` constant and the `Permission:Documents.Restore` localization key in the four resource files are gone. `Documents.Restore` had existed since v0.3.0.

  > **Migration:** grant **`VaultExtract.Documents.Delete`** to any role, user or OAuth client that needs to restore documents of every type, and drop references to the `VaultExtractPermissions.Documents.Restore` constant, which no longer compiles — or, in an Angular host, to `EXTRACT_PERMISSIONS.Documents.Restore`, which is gone from `@dignite/ng.vault-extract` too. A role holding `Documents.Restore` without `Documents.Delete` loses role-level restore and keeps restore of its own documents through ownership; a role holding `Documents.Delete` without `Documents.Restore` gains restore, which is the intended "whoever may delete may undo". Stored grant rows that still name `Documents.Restore` become inert — ABP ignores undefined permissions — so no data step is needed.

- **AI re-classification needs the right to assign any type** ([#648](https://github.com/dignite-projects/vault-extract/issues/648)). `RerecognizeAsync` was judged by `Edit` on the document alone, but the classifier it re-runs may land the document in **any** type of the layer — so a caller holding only an `Upload` grant on one type could move their own document into a type they may not upload into, and a type-level `Edit` grant holder could push another user's document out of the type the grant was given on. It now makes the same pair of judgments a manual classification makes: `Edit` on the document, then `DeclareType` on the **empty subject**, which leaves only that row's role-level arm — `Documents.ConfirmClassification` or `Documents.Upload` — exactly as an untyped upload is judged. No new permission, no new rule, no schema change. A caller whose right to assign types is per type uses Confirm / Reclassify and names a type their `Upload` grant covers. `RetryPipelineAsync` is unchanged: a classification run exists only because an untyped upload or a re-classification started it, and both now require the role-level right. **Not breaking against v0.3.2**, where the method required `Documents.ConfirmClassification` outright. In the operator UI the detail page's **Re-recognize** button follows the same OR, and the per-reason review hints under the review banner now render only for a caller who may edit or review the document — an owner locked out for review was being told to do something they could not, beside the line saying to wait for a reviewer.

- **The role-level document permissions' display names pair with their type-level counterparts** ([#645](https://github.com/dignite-projects/vault-extract/issues/645)). Display names only, in all four resource files; the permission names are frozen contracts and do not change. `Documents.ConfirmClassification` reads "Edit Documents of All Types" (编辑所有类型的文档), which is what it grants, instead of "Confirm Classification"; `Documents.Delete` reads "Delete Documents of All Types" (删除所有类型的文档); `Documents.Upload` reads "Upload into All Document Types" (上传到所有文档类型). Each now pairs with the per-type grant it is the all-types form of — "Edit / Delete All Documents of this Type", "Upload into this Document Type" — the way `Documents.ReadAll`'s "Read Documents of All Types" already did. ja and zh-Hant follow each file's existing wording of the type-level names.

### Fixed

- **Seed contributors now honour the tenant they seed for** ([#640](https://github.com/dignite-projects/vault-extract/issues/640)). `VaultExtractHostRoleDataSeedContributor` ignored `DataSeedContext.TenantId`: `IdentityRole`'s `tenantId` constructor parameter defaults to `null`, so every tenant ever created added a duplicate `DocumentManager` / `Viewer` pair to the Host layer instead of getting its own, and the permission grants that followed were written against a role name the tenant layer had no row for. It now seeds inside `CurrentTenant.Change(context?.TenantId)` and constructs each role with that tenant id, matching ABP's own `IdentityDataSeeder`. `VaultExtractSampleDataSeedContributor` had the mirror defect — it documented itself as Host-layer-only but switched into the tenant scope anyway, so a tenant-scoped seed missed the Host-layer sample `Document` under its tenant-filtered lookup and inserted a second row under the same fixed primary key; it now returns early whenever `TenantId` is set and seeds explicitly under `CurrentTenant.Change(null)`. `VaultExtractHostDbMigrationService` now re-seeds every existing tenant after the Host seed (when multi-tenancy is enabled), so a tenant created before this fix — which never received its roles — gets them retroactively; re-running the migrator against an already-seeded tenant changes nothing.

  > **Deployment:** the duplicate Host-layer roles this bug already produced are data, not code, and are not cleaned up automatically — delete one `Viewer` and one `DocumentManager` from the Host layer by hand. Grants are keyed by role *name*, so whichever row survives keeps its permissions.

- **The provider-key search dropdown in the resource-permission dialog is no longer see-through on hover** ([#642](https://github.com/dignite-projects/vault-extract/issues/642)). ABP's lookup component paints it with `--lpx-content-bg`, which LeptonX Lite never defines; the host stylesheet now bridges it to `--lpx-card-bg`, the theme's card surface.

### Changed

- **BREAKING — field architecture v2 storage is removed** ([#593](https://github.com/dignite-projects/vault-extract/issues/593), closing [#558](https://github.com/dignite-projects/vault-extract/issues/558)). - **BREAKING — the Angular library is renamed `@dignite/vault-extract` → `@dignite/ng.vault-extract`**, matching the `@dignite/ng.*` convention the sibling Angular packages already follow (`@dignite/ng.flex-fields`, `@dignite/ng.flex-fields-ckeditor`). The npm workspace alias to GitHub Packages (`npm:@dignite-projects/...`) is dropped now that the real `@dignite/*` packages are live on npmjs, closing the npmjs-availability blocker from [#577](https://github.com/dignite-projects/vault-extract/issues/577).
- **The npm install no longer needs a registry credential.** With the alias gone, every dependency resolves from npmjs, so the `@dignite-projects` scope mapping and its `${GITHUB_TOKEN}` placeholder are removed from `angular/.npmrc` and the `PACKAGES_READ_TOKEN` drops out of both workflows' `npm ci`. The npm counterpart of [#595](https://github.com/dignite-projects/vault-extract/pull/595), which did this for the .NET restore. Publishing a pre-release to GitHub Packages still authenticates, in the publish step's own config.
- **The dependency stack moves forward as a batch**: OpenTelemetry 1.13/1.15 → 1.18, EF Core tooling 10.0.2 → 10.0.11, `Microsoft.Extensions.AI` 10.6 → 10.9, `Microsoft.Agents.AI` 1.8 → 1.20, plus Fody, Source Link, Serilog, Markdig and the test stack (Test SDK 17.14 → 18.9, `xunit.runner.visualstudio` 3.1 → 4.0, NSubstitute 5.3 → 6.2). ### Added

- **A build guard that fails when the published bundle imports a package the published `package.json` does not declare** ([#577](https://github.com/dignite-projects/vault-extract/issues/577)). ng-packagr externalises every bare specifier it does not bundle but never checks that the externals are declared, so this class of defect is silent through build, `npm install`, and CI — it only surfaces when a consumer builds their own app. Runs in CI and as part of `npm run build:vault-extract`. Ported from the sibling `abp-modules` repo; it is what found the `@abp/ng.components` omission below.
- **A deployment runbook for the field architecture v2 → v3 data migration** ([#561](https://github.com/dignite-projects/vault-extract/issues/561)), covering what the migrator is (module-level, additive, idempotent, one tenant layer per call), who invokes it, the measure / apply / migrate / verify sequence, four verification queries, and the rollback boundary. Required reading before taking this release — see the BREAKING entry above.

### Fixed

- **The pre-release npm publish failed on the dist-tag.** npm/cli rejects a prerelease version whose dist-tag is left at its default — the check is on whether `--tag` was passed at all, not on its value — so the release workflow's GitHub Packages step now passes `--tag latest` explicitly. `latest` is correct for that registry: it only ever receives pre-releases (stable goes to npmjs under the public `@dignite/*` name), so it tracks the newest preview and an unpinned install keeps resolving. The step was green through `0.5.0-preview.2` because the npm it installs has since picked up the check.
- **Field queries lost four of v2's fail-closed guards in the v3 switch** ([#593](https://github.com/dignite-projects/vault-extract/issues/593)). `DocumentFieldQueryResolver` + `DocumentFlexFieldQueryExecutor` replaced `IDocumentRepository.GetFieldMatchedIdsAsync` without carrying over the rejections for a range filter on an unordered field type, a value that does not parse as its declared type, an offset-bearing `DateTime`, and a wholly empty filter. v2's integration tests kept passing throughout because they exercise `GetFieldMatchedIdsAsync` directly, which nothing on the live path calls — vouching for dead code while the path that runs went untested. All four guards are restored, expressed on `FlexFieldValueType` rather than a per-field-type switch, and the cases are ported onto the v3 path; each guard was mutation-tested before landing.
- **The Angular library did not declare `@abp/ng.components`**, which its bundle imports (`@abp/ng.components/extensible`) in five components. It is not reachable transitively: `@abp/ng.components` peer-requires `ng.core` / `ng.theme.shared` rather than being pulled in by them, so a consumer without their own direct dependency on it got an unresolvable specifier. The same shape as the `@dignite/ng.flex-fields` omission that opened #577.
- **The library declared no Angular peer dependencies at all.** `@angular/common` / `core` / `forms` / `platform-browser` / `router`, `rxjs`, `@ng-bootstrap/ng-bootstrap` and `@ngx-validate/core` are now declared as peers, stating the versions the library is actually built against instead of leaving a consumer to infer them.

## [0.3.2] - 2026-08-23

Patch release for the 0.3.x stable line. This release closes a silent field-extraction truncation on large multi-value fields (a production bank-statement document lost the tail of a transcribed table with no error signal), and fixes a cluster of vision-LLM OCR and PDF ruling-line issues surfaced by the same document — LaTeX-table / layout-annotation cleanup, no-content-refusal normalization, and stacked per-row table-box detection.

### Fixed

- **Field extraction silently truncating large multi-value fields** — `FieldExtractionWorkflow` never set `ChatOptions.MaxOutputTokens`, so SiliconFlow silently applied its own ~4096-token default completion cap; even once sized (CJK-aware, since field values preserve the document's original wording and `DefaultLanguage` defaults to Japanese), the OpenAI SDK serializes it as `max_completion_tokens`, which SiliconFlow's endpoint doesn't recognize and silently ignores instead of erroring. A `DelegatingHandler` on the host's SiliconFlow `HttpClient` now rewrites the outgoing request body to the legacy `max_tokens` field it does understand; a response cut off at the limit (`FinishReason.Length`) also now logs a distinct warning instead of degrading with no diagnosable signal.
- **Chat-client HTTP hangs from stale pooled connections** — the host's OpenAI-compatible `HttpClient` now bounds `PooledConnectionLifetime` to 5 minutes and raises `NetworkTimeout` to 300s (with the SDK's own 100s `HttpClient.Timeout` disabled, since it was silently overriding `NetworkTimeout` back down to 100s), closing a failure mode where a NAT/proxy-dropped idle connection hung every request that reused it for the full timeout before ABP's retry loop re-queued the job.
- **VisionLlm OCR: LaTeX tables and leaked layout annotations** — a vision LLM (observed on Qwen3-VL), trained heavily on academic document datasets, still rendered line-item tables as `\begin{tabular}` and occasionally leaked an internal bounding-box HTML comment into the transcription, despite the prompt requiring GitHub-Flavored Markdown and forbidding both. `VisionLlmOutputGuard` now deterministically rewrites `\begin{tabular}` blocks to GFM tables and strips HTML comments, the same fix pattern as the existing code-fence stripper (#448).
- **VisionLlm OCR: single-page running-header/footer judgment** — the prompt now asks the model to judge boilerplate by position and style rather than by confirmed repetition (a single-page call can never confirm repetition across pages), closing a case where a page-bottom confidentiality line and page number survived transcription.
- **VisionLlm OCR: no-content refusals inlined as transcribed text** — despite the prompt asking for no output at all on an unreadable image, the model sometimes returned an English refusal sentence instead, which was then treated as real content and occasionally misjudged by sub-document segmentation as a standalone document (observed on two purely decorative images in a bank-statement PDF). `VisionLlmOutputGuard.LooksLikeNoContentRefusal` now normalizes a detected refusal to an empty result, length-gated so real (longer) transcriptions can never be misclassified; the segmentation prompt also now treats a confirmed-empty embedded-image OCR result as never a standalone document.
- **PDF ruling-line grid detection missed stacked per-row table boxes** — some report engines (observed on a Japanese bank-statement PDF) draw a table's grid as many small per-row rectangles rather than continuous ruling lines, which `DetectGrids` silently dropped, falling back to the less reliable whitespace-heuristic path and mis-clustering rows. `ChainStackedRowBoxes` / `ChainCollinearVerticalSegments` chain these leftover shapes into valid rule candidates.

### Changed

- **`SlugSuggestionAppService` moved off the `Structured` keyed chat client onto `TitleGenerator`** — `Structured` is now reserved for classification and field extraction, the accuracy-sensitive callers where mis-output is user-visible, so it stays pinned to a strong model rather than trimming cost; slug suggestion's single-shot, prompt-unique-per-call shape matches `TitleGenerator`'s existing usage instead.

## [0.2.0-preview.2] - 2026-06-25

Preview of the 0.2.0 line. This release rebrands the project to **Dignite Vault Extract** and is dominated by the container / sub-document model and a major expansion of structure-aware text extraction (PDF / DOCX / PPTX). As a `0.y.z` pre-release the exit contracts may still change — see [CONTRIBUTING → Versioning and releases](CONTRIBUTING.md#versioning-and-releases).

### Changed

- **BREAKING — package identifiers renamed to the `Dignite.Vault.Extract.*` prefix** (consolidating the earlier `Dignite.DocumentAI` → `Dignite.Extract` cutover, #370 / #382). NuGet package IDs and namespaces moved, and the Angular library is now published as `@dignite/vault-extract`. Downstream consumers must update package references, `using` directives, and npm dependencies.
- Rebranded the UI to the DIGNITE badge — new logos and favicons, restored default ABP typography (removed the ProstoOne font).
- Collapsed the review queue into a list filter + detail remediation flow (#395).
- Enforce document-type layer-scoped uniqueness in the application layer (#304).

### Added

- **Container & sub-document model** — a document can now be recognised as a *container* and segmented into derived sub-documents, with full provenance on the MCP and Angular egress:
  - Container document concept and born-digital container segmentation (#346, #347, #351).
  - Route embedded figures to derived sub-documents and persist them as Scenario B candidates (#306, #344, #345); parent-aware figure gate (#365, #369); unified figure routing + born-digital segmentation (#371, #375).
  - Sub-document discovery by `OriginDocumentId` and a "view sub-documents" container filter (#354, #360, #363).
  - Retract sub-documents when a container is reclassified, and emit `DocumentReclassifiedToContainerEto` on type→container re-recognition (#349, #352, #355, #362).
- **Structure-aware text extraction**:
  - Extract embedded raster images from digital PDFs via `IOcrProvider` (#301, #311).
  - DOCX embedded-image extraction + OpenXML-to-Markdown structural rebuild (#308, #323).
  - PPTX embedded images, charts, tables & speaker-notes extraction via OpenXML (#307, #314).
  - Column-aware PDF reading order via PdfPig document-layout analysis (#310, #326); reconstruct digital-layer tables into Markdown tables (#329, #340).
  - Map PDF font size/weight to Markdown headings and carry bold/italic runs into emphasis (#403); strip running headers/footers and page numbers (#383); keep figure OCR markers as egress provenance annotations (#381); skip the full-page scan background of searchable / sandwich PDFs (#309, #324).
- Duplicate re-upload detection via field fingerprint, gating the `DocumentReadyEto` event (#411).
- Document AI overview statistics (#333, #341) with cabinet and document-type overview cards (#335, #342) and an upload-first home page (#332, #339).
- Initial EF Core database migration for the host.
